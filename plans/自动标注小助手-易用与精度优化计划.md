## 二、结论：现在这条路会卡在哪（按严重度）

### 拦截级（不修就跑不通）

1. **「手办」在本机路径会静默出错，不是报错，是给你一堆假结果。**
   内置词表（`inference/vocab/*.npz`）是**工地/街景口径**：`安全帽 / 挖掘机 / 反光背心 / 交通标志…`（`inference/tools/build_vocab.py:19-63`，`ALIASES` 全文无「手办/公仔/玩偶/玩具」）。未命中别名表时，代码会走到 `encode_vocabulary`（`inference/worker.py:150`）**直接拿中文去 CLIP 编码** —— 而 `worker.py:123-124` 自己写着「直接编码中文会得到没有意义的向量（实测『人』一个目标都查不到）」。即：用户输入「手办」，软件不报错、不提示，返回近乎空的框。
2. **一切标注都要求先有「能调工具的对话模型」。**
   `ChatPanel.tsx:139` 没选对话接口+模型就不让发送；`agent/orchestrator.ts:181` 再要求工具能力已 `verified`。于是首屏那条「**用内置模型标注（无需 API Key）**」（`OnboardingLanes.tsx:47`）是假的：它跳到的页面和云端那条**完全一样**（`settings/'ai'`），而且真的仍然要 API Key。
3. **类别没有一等公民入口。**
   新建项目对话框只有「项目名称」（`ProjectResolveDialog.tsx:38`）；类别只能靠对话里让 Agent 调 `set_project_classes`，或去项目概览的「类别与点位模板」。对话模型不能用 = 类别建不出来 = 整条链断在这里。

### 精度级（能跑但标不准）

4. **4K 竖屏小目标 + 同款干扰物，整图送模型必然偏松。**
   手办只占画面一小块，同框的大号毛绒公仔是外形相近的强干扰。软件目前**没有任何裁剪/分块/放大手段**：`Runs.java:164-168` 直接把整张原图 base64 发出去（`data:image/png;base64`），坐标也只按原图基准校验（`Runs.java:193`）。区域/切片几何**只存在**于数据集版本（`DatasetTransforms.java`），没接到标注运行上。
5. **本机小目标必然漏检。**
   `conf 0.25 / iou 0.7 / imgsz 640 / maxDet 300` 写死两处（`engine/.../LocalInference.java:95`、`inference/worker.py:603-606`），**界面完全不可调**（只有评测的 IoU 阈值能改）。4K 帧缩到 640 后，小手办只有几十像素。
6. **没并发出去的「无目标」无法区分对待。**
   模型返回空数组是合法结果（`Runs.java:156` 契约里写明），但审核时看不出哪些帧是「真的没有」、哪些是「模型没看见」，无法只重跑可疑帧。

### 繁琐级（每天都多花时间）

7. **视频导入 6+ 步**：`导入视频` → 项目确认框 → 抽帧面板 → 选密度 → 开始抽帧 → 等 → 自动入库（`ChatHome.tsx:87-135`、`VideoImport.tsx`）。
8. **审核只能一张张来**：候选/确认是**素材级**（`AssetAnnotator` 的「保存 / 保存并确认」），勾选多张后的唯一动作是「在对话里处理这些素材」（`ProjectOverview.tsx:137-146`，全仓库无任何「批量确认/全部确认」）。23 帧 = 23 次双击 + 23 次确认。
9. **抽帧只有固定密度**：`interval / every_n / fps`（`engine/.../VideoFrames.java:112,117`），60 fps 手持视频按 1 秒抽会得到大量近乎重复的帧（这次 22 秒 → 23 帧、71 MB），重复帧既费请求又拉长审核。
10. **小目标人工精修难**：工作区里已有一份**未提交**的画布缩放改动（`renderer/src/QualityCanvas.tsx`，注释就写着「小目标（例如视频里的手办）在整图视图中很难精确拖框」）—— 说明这条痛点已经被撞到，但还没落地。
11. **本地错误码不可行动**：`vocabulary_encoder_missing` 这类码不在任何 UI 映射表里（`renderer/src/reasonCodes.tsx`、`mediaErrorMap.tsx`），只能以纯文本出现，没有「去模型库」按钮。
12. **项目任务类型硬编码 `detect`**（`ChatHome.tsx:60`、`Sidebar.tsx:207`），分割/关键点/旋转框/分类项目从界面根本建不出来；「轨迹标注」tab 对非 detect/pose 项目禁用且**不给原因**（`Tasks.tsx:78`）。

## 三、判断（本方案的技术取向）

- **要「准」，这一轮主力是云端视觉模型 + 两个手段：一张人工参考帧（few-shot）＋ 只标「中间那块区域」的裁剪**。裁剪让目标在送出的图里相对放大数倍，是解决小目标最直接的办法，同时体积更小、更省钱。
- **要「不花钱」，本机路径必须先把两个硬伤修掉**：中文类别名英文化（含显式拒绝，不再静默出错）＋ 小目标模式（提高 imgsz／可选切片）。诚实说：YOLO-World 零样本在「桌面杂物 + 同款毛绒公仔」这种场景里大概只能到「差不多」，真正又准又免费的解是**后续用十几张手标帧微调一个小检测器**（软件已有训练链路），本轮不做，列为后续。
- **要「方便」，最高杠杆的一刀是：标注不再必须经过对话模型**（直达标注入口），类别与口径直接在界面上填。

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| 测试接口的模型其实是纯文本模型，根本不能看图 | 第 1 步先验证；标注模型下拉显式标注「未通过图片输入验证」，并给「改选视觉模型」的出口 |
| 区域裁剪改变坐标基准，坐标写错会污染数据集 | 逆映射回原图后再走既有 `Annotations.validate`；越界即失败；区域冻结进运行快照保证可复现 |
| 扩充词表要重新生成 npz（构建期需 CLIP 权重） | 别名表与向量表解耦：加中文别名不必等 CLIP；npz 重新纳入 `check:models` 哈希校验，打包前卡住 |
| 解耦词表可能影响既有三级词表验收 | 保持返回体 `vocabularySource` 口径不变，只把「未命中别名表的中文」从静默编码改为显式拒绝 |
| 改发送尺寸可能影响既有媒体验收 | 默认只作用于「发送副本」这一层；抽帧产物仍是无损 PNG，既有断言不涉及发送副本 |
| 批量确认可能覆盖人工成果 | 复用 `protectedHuman` 语义 + 执行前清单 + 反向用例 |
| 4K 帧 71 MB 占盘 | 场景抽帧减少帧数；发送副本有界；沿用既有磁盘余量保护与空间维护 |

- 不改指标算法（`Matching.java`）、真值集机制与导出格式
