## 源码态启动后窗口不显示（同日，已修复）

用户要求「启动软件界面看看还要做什么」，`node scripts/desktop-start.mjs` 启动后**窗口始终不可见**。

- 现象：主进程（browser）、renderer、network utility 三个进程都在跑，Java 引擎正常起来，`autolabel.db-wal`
  与 `%APPDATA%\自动标注小助手\Preferences` 都被写入，renderer 累计 3.7 s CPU —— 页面确实加载并执行了，
  但 `Get-Process electron | MainWindowHandle` **恒为 0**。
- 根因：`desktop/main.ts` 的 `createWindow()` 里窗口以 `show: false` 创建，**唯一**的显示时机是
  `window.once('ready-to-show', () => window.show())`。本机 Chromium GPU 进程不可用（软件渲染）时首帧不提交，
  `ready-to-show` 不触发，窗口永远隐藏 —— 应用只剩托盘图标。项目里所有冒烟/UI 检查之所以正常，是因为它们
  自己显式调用了 `window.show()`（`--desktop-window-check`、`smoke()` 里的截图路径），掩盖了这条路径的缺陷。
- 修复：`createWindow()` 增加 `window.webContents.once('did-finish-load', ...)` 兜底（仅在未可见时 show），
  保留 `ready-to-show` 作为常规路径。`npm run build:desktop` 后启动即正常显示，句柄非 0、标题
  「自动标注小助手 · AutoLabel…」。**改动很小但属启动主链路，后续若重排窗口显示逻辑不要回退掉这个兜底。**
- 排查手法（本机沙箱限制下的可用组合）：`Get-CimInstance Win32_Process` 看 `CommandLine` 区分
  browser/renderer/utility 并确认 createWindow 确实执行；`Get-Process MainWindowHandle` 交叉验证，
  用 WorkBuddy/explorer 等已知有窗口的进程当对照，避免把"枚举失效"误判成"窗口不存在"。
  `Add-Type`、`New-Object -ComObject WScript.Shell`、`AppActivate` **全部被沙箱拦截**，不要在这些上浪费时间。

  任何外部命令都失败；本轮排查全部改用 PowerShell，输出一律 `Out-File` 落盘再 Read。
- 收尾：本次探测用的临时文件（`tmp/qa-*.txt`、`tmp/app-launch.log`）已用 `[IO.File]::Delete` 即时清除；

用户在界面上删除项目，第 3 步「删除选项」点「删除项目」后报
`[engine_data_maintenance_locked] 引擎正在维护数据，暂不接受新的写入或模型调用。`

- **根因（两侧都没接上）**：桌面端 `deleteProject()` 先 `storage.createBackup()` 做备份，再
  `storage.withMaintenance(() => engine.request('project.delete', payload))` —— 即**在持有数据维护锁的情况下**
  调用 `project.delete`。而引擎 `Maintenance.enter()` 会拒绝维护期间的一切写入命令（该命令不在任何豁免名单里），
  于是「自己锁住了自己」。引擎侧本有「持有维护锁的动作」通道（`DATA_ACTIONS`，必须回传当前锁归属
  `operationId`），但名单里**只有 `backup.create` / `restore.prepare`**，没有 `project.delete`；
  桌面侧 `withMaintenance` 也**没把 operationId 传给动作**。任一侧单独补齐都不够。
- **修复（4 处，共 ~10 行）**：
  1. `Maintenance.java`：`DATA_ACTIONS` 增加 `"project.delete"`；新增 `static boolean isDataAction(String)`，
     避免名单在调度层再抄一份。
  2. `Engine.java`：调度分支由 `command.equals("backup.create")||command.equals("restore.prepare")`
     改为 `Maintenance.isDataAction(command)`。
  3. `storage.ts`：`withMaintenance<R>(action: (operationId: string) => Promise<R>)`，把本次维护锁的 operationId
     交给动作（`owned` 本来就提供，只是之前被丢弃）。
  4. `main.ts`：`engine.request('project.delete', { ...payload, operationId })`。
     注意桌面 `validation.ts` 的 schema **不需要**加 operationId —— 校验发生在渲染进程载荷上，

## 交付前检查：启动自动拉起引擎 + 引擎断连修复（同日，用户要求）

用户要求「全面检查整个软件项目，确保端到端全流程跑通；重点实现运行软件时自动启动引擎、修复引擎断连」。

- **根因 1（核心）：虚拟线程载体池被占满 → 引擎整体失联。** 命令处理器在虚拟线程上运行，引擎内多处
  `synchronized`（典型 `Projects.importAssets`）里做耗时工作；JDK 21 下会 **pin 载体线程**，载体数默认 =
  逻辑 CPU 数（本机 16）。占满后 ForkJoinPool 无法调度任何虚拟线程，**连 `/health` 都执行不了**。
  实测：16 并发导入期间 `/health` 9/9 采样全部超时、任务结束才恢复；加
  `-Djdk.virtualThreadScheduler.parallelism=64` 后同样场景 9/9 全部 200。
- **根因 2：JDK 内置 HTTPServer 对「半截请求」零容忍。** 15 条只发一半请求体的连接即可让引擎**永久**失联
  （默认参数下 20 秒后仍超时、关闭连接也不恢复）；加 `maxReqTime=20` + `idleInterval=10` 后 2～3 秒自愈。
  关键反证：`maxReqTime=1` 时 6.96 秒、240 张的批量导入仍完整成功 → 该超时只约束接收请求，不误杀长任务。
- **根因 3：崩溃后无任何自动恢复。** 子进程退出或启动握手超时后只置 `error`，其后所有命令直接抛
  `ENGINE_UNAVAILABLE`；`start()` 遇已退出的陈旧 `child` 引用还会永久短路。已加有界自动重启（≤5 次，
  1s→30s 退避，成功归零；显式 stop 撤销待执行重启），并在「事件流 + 健康检查同时失败」时升级为重建进程。
- **根因 4：后台调度与存储闩锁会把引擎「变哑」。** `Runs.tick()` 的 `flowTick.run()` 无兜底 →
  `ScheduledExecutorService` 静默停止后续执行（HTTP 与健康检查都正常、但任务永不推进）；
  `storagePaused` 与 `Store.writeFailed` 都是单向闩锁，一次瞬时 `SQLITE_BUSY` 即永久停摆。
  已改为逐步兜底 + 30 秒冷却自愈 + 只对不可恢复存储错误（只读/IO 错/损坏/磁盘满/无法打开/非数据库文件）置位。
- **其他加固**：`/health` 与图片流不再占 16 个命令许可；SSE 循环体兜底 `RuntimeException`、心跳 10s→5s；
  关停链 `try/finally` 保证 `countDown()`；HTTP 处理器补 `catch(Throwable)`（OOM 不再让客户端只能等超时）；
  `Engine.close()` 各步骤独立兜底以保证 `store.close()` 执行；先出窗口再启动引擎（此前最长 30 秒无界面）；
  `before-quit` 保证 `engine.stop()` 无条件执行（否则留下占用数据库的 Java 孤儿进程）；
  `powerMonitor.resume` 不再因存储忙丢事件；原图目录在引擎不可用时如实回传 `pending-restart`；
  客户端加在途命令闸门（上限 12）、事件流失败升级探测 `/health`、`secretValues` 定长、优雅停止 2.5s→8s。

### 关键发现：`Store.backupBeforeMigration` 一直就是坏的
- 现象：新写的迁移用例抛 `migration_backup_failed`，原因 `cannot VACUUM - SQL statements in progress`。
- 定位：`VACUUM INTO` 用的是调用方 `writer` 连接，而该连接此刻仍握着读 `user_version` 与设 `journal_mode` 的语句。
- **不是本次引入**：仓库自带的 `EvaluationTest.migration`（`evaluation` 范围）与 `FlowIntegrationTest.migration`
  （`flow-integration` 范围）在改动前就是同一个错误。长期没被发现，是因为 `-TestScope all` 根本不跑这两个迁移用例；
  改动前先跑了一次 `flow-integration` 复现，才敢下这个结论。
- 后果：**任何一次 schema 升级都会在已有数据目录上失败并让引擎拒绝启动**，而本次正好要升 10 → 11。
- 修法：`try(Connection source=connect(); PreparedStatement ...)` 另开连接取快照；并把失败原因拼进错误消息
  （原来只有一句「请检查磁盘空间与备份目录权限」）。修复后 `evaluation` / `flow-integration` 双双转绿。
- 排查手法值得复用：**不要猜，先把被吞掉的异常原因暴露出来**（给 `ApiError` 消息补 `e.getMessage()`），一次定位。
